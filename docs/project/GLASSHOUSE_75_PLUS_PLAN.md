# 온실 첫 번째 출시 세트 구성·성능 기획서

작성일: 2026-09-14
상태: 사용자 검토용 제안. 콘텐츠 및 디자인 제작 승인 전.

최신 확정 변경: 대표 그림체·색감은 사용자 승인 완료. 화분+식물처럼 분리 시 겹침·원근·가림 문제가 생기는 조합은 일체형 스티커 1개로 제작한다. 아래 목록의 분리 제안보다 이 원칙이 우선한다.

## 1. 확정 요구사항과 제안 범위

- 모든 출시 세트는 독립적으로 배치할 수 있는 스티커를 최소 75개 제공한다. 난이도 구분과 스티커 카테고리 UI는 없다.
- 최소 수량은 성능 문제를 이유로 낮추지 않는다. 75개에서 성능 기준을 충족하지 못하면 자산과 앱을 최적화하고 재검증한다.
- 첫 온실 세트는 80개를 제작 검토안으로 제안한다. 최종 제공 수량은 75개 이상을 유지하면서 실제 자산·기기 측정 후 확정한다. 80개나 100개를 새 고정 상한으로 약속하지 않는다.
- 복제, 색상만 바꾼 반복, 배경에 그려진 사물, 움직임 프레임은 별도 스티커 수로 세지 않는다. 식별 가능한 독립 배치 항목으로 센다.
- 출시 전체 목표는 3개 테마 × 2개 세트, 총 6세트다. 최소 450개 세트별 배치 항목이 필요하지만 이를 450개 고유 원화로 표현하지 않는다. 세트 간 재사용은 별도 기록한다.
- 이번 문서는 첫 온실 세트의 목록·조립 원칙·성능 목표를 제안한다. 실제 이미지 제작이나 성능 측정 완료를 뜻하지 않는다.

## 2. 콘셉트와 장면

가제: 햇살을 모으는 온실 / Sunlit Greenhouse Atelier.
한국의 20대 여성과 중고등학생을 주요 이용자로 고려한 조용한 원예 작업실이다. 따뜻한 목재, 세이지 그린, 크림색을 중심으로 개별 오브젝트를 조립하는 재미를 제공한다.

왼쪽에는 식물 선반, 오른쪽에는 원예 작업대, 앞쪽에는 작은 휴식 공간을 둘 수 있도록 충분한 빈 공간을 둔다. 완성 예시는 제안일 뿐이며 정답 위치나 점수는 제공하지 않는다. 배경은 바닥·벽·유리창 같은 고정 건축 요소만 포함하고 배치 가능한 물건을 미리 그려 넣지 않는다.

정식 세트는 빈 배경과 80개 미사용 목록으로 시작하는 안을 제안한다. 완성 예시는 별도 미리보기로 제공한다. 현재 9종 통합 시제품의 기본 배치는 유지하며 정식 세트와 저장 공간을 분리한다.

## 4. 조립과 이미지 제작 기준

- 선반·작업대 구조는 일체형으로 유지하고, 책·도구처럼 독립 배치가 자연스러운 물건을 분리한다. 판자나 나사까지 쪼개 수량을 늘리지 않는다.
- 화분+식물뿐 아니라 꽃병+꽃, 트레이+내용물 등에서도 분리 시 겹침·원근·가림 문제가 생기면 하나의 완성된 오브젝트로 제작한다. 사용자가 미세 조립해야 하거나 별도 마스크·복잡한 레이어 처리가 필요한 조합은 통합한다.
- 통합 오브젝트는 구성물 수와 무관하게 스티커 1개로 계산한다. 현재 09+15 통합으로 유효 제안 수량은 79개다. 추가 통합 후 75개 미만이면 새로운 독립 소품을 보충하여 최소 75개를 충족한다. 기존 80개 표의 번호는 추적용으로 유지한다.
- 큰 가구는 뒤쪽, 소품·식물은 중간, 받침·러그는 아래쪽을 기본 레이어로 제안하되 사용자가 변경할 수 있다.
- 모든 자산은 동일한 시점·광원·그림자 강도를 사용하고 흰색 외곽 테두리를 넣지 않는다. 투명 가장자리의 밝은 띠는 밝은 배경과 어두운 배경에서 모두 확인한다.
- 작은 물건은 모바일에서 선택할 수 있는 터치 영역을 별도로 확보한다. 작은 그림을 억지로 확대해 장면 비례를 깨뜨리지 않는다.
- 원본 제작 파일과 서비스용 파일을 구분한다. 서비스용은 투명 여백을 줄이고 표시 크기에 맞춰 축소한다. 모든 자산에 동일한 대형 해상도를 적용하지 않는다.
- 제작 초기 해상도 검토안: 작은 물건 긴 변 256~512px, 중간 물건 512~768px, 큰 가구 768~1024px. 확대 및 PNG 출력 품질을 확인하고 개별 조정한다. 형식은 투명 PNG/WebP 후보를 실제 내보내기 호환성으로 비교한다.
- 썸네일은 별도 작은 파일을 사용한다. 자산별 고유 ID, 한국어·영어 이름, 원본/배포 파일, 크기, 기준점, 초기 배율, 레이어, 권리 기록을 관리한다.
- 승인 순서: 배경과 대표 조립 장면 → 선반·화분·책·도구의 대표 시안 → 전체 제작. 신규 디자인은 사용자 확인 후 제작한다.

## 5. 목록과 편집 경험

카테고리 없이 미사용 스티커를 고정 순서로 표시한다. 배치에 성공하면 목록에서 빠지고, 삭제하면 원래 순서로 돌아온다. 실행 취소·다시 실행·재접속 복원도 같은 규칙을 따른다. 배치 실패나 취소는 목록을 변경하지 않는다.

한 항목은 한 번 배치한다. 모든 항목을 배치해도 추가 구매나 초기화를 유도하지 않고 삭제하여 다시 쓸 수 있음을 안내한다. 목록 가상화나 지연 로딩을 적용하더라도 키보드 탐색과 드래그가 끊기지 않아야 한다.

기존 사용자 작품을 지우거나 기존 ID를 변경하지 않는다. 정식 세트에는 별도 ID와 버전을 부여한다. 기기 저장에는 위치·크기·회전·사용 상태를 복원할 데이터만 저장하고 이미지 본문은 넣지 않는다.

## 6. 애니메이션과 소리

특별 효과 후보는 랜턴의 은은한 빛, 풍경의 가벼운 흔들림, 고양이 호흡, 나비 날갯짓이다. 기본 스티커 개수는 효과 유무와 무관하다. 첫 검증에서는 동시에 움직이는 항목을 최대 3개로 제한하는 안을 시험한다. 정지 상태도 완성된 그림이어야 한다.

사용자는 움직임을 끌 수 있으며 기기의 동작 줄이기 설정을 존중한다. 숨겨진 탭에서 움직임과 소리를 중단하고, 낮은 성능에서는 효과 빈도·동시 실행을 줄인다. 이미 배치한 스티커 수나 그림을 줄여 성능을 맞추지 않는다.

배경음 후보는 온실 환경음과 잔잔한 악기 음악이며 아직 음원 확정은 아니다. 현재 화면에 어울리는 추천 곡, 추가된 다른 곡 선택, 배경음 없음, 전체 음소거와 음량을 제공한다. 효과음과 배경음은 각각 조절하는 안을 제안한다. 처음에는 무음이며 사용자의 재생 동작 후 시작한다. 추가 음원은 ID·제목·길이·반복 구간·사용 권리·파일 크기를 기록하고 선택한 곡만 불러온다.

PNG에는 배경과 스티커의 정지 모습을 저장하며 음악은 포함하지 않는다. 애니메이션은 지정된 정지 프레임으로 합성한다. 음악이 포함된 영상 저장은 별도 후속 범위다.

## 7. 성능 예산과 출시 판정

아래 수치는 측정 결과가 아닌 개발용 초기 목표다. 실제 중저가 Android와 iPhone, 데스크톱에서 장면 품질과 함께 확인한 뒤 지원 기기와 예산을 확정한다. 기기명·OS·브라우저 버전·화면 크기를 기록하고 브라우저 화면 축소만으로 실기기 검증을 대체하지 않는다.

| 항목 | 초기 목표 / 판정 방법 |
|---|---|
| 최소 제공 수량 | 실제 독립 자산 75개 이상, 전부 동시 배치 가능 |
| 기본 검증 규모 | 75개와 제안 80개, 효과 끔/켬 각각 검사 |
| 확장 검증 | 100개는 부하 시험용 후보. 통과해도 모든 세트의 필수 수량으로 삼지 않음 |
| 첫 조작 가능 시간 | 캐시 없는 10Mbps·왕복 지연 100ms 시험에서 5초 이내 목표, 음원 제외 |
| 초기 내려받기 | 앱·배경·첫 화면 썸네일 합계 3MB 이내 목표, 나머지 지연 로딩 |
| 세트 이미지 총 전송량 | 80개 서비스용 이미지+배경+썸네일 12MB 이내 목표, 음원 별도 |
| 조작 반응 | 실제 기기에서 입력 후 시각 반응 95백분위 100ms 이내 목표 |
| 드래그 | 75/80개 배치 상태 30초 드래그에서 프레임 간격 95백분위 33ms 이내 목표, 데스크톱 60fps 지향 |
| 저장·복원 | 조작 중 저장으로 멈추지 않고 마지막 확정 동작 복원. 자산 로딩 후 복원 2초 이내 목표 |

| 이미지 메모리 | 디코딩된 이미지 추정 합계 96MiB 이내를 초기 예산으로 검토. 전체 앱 메모리와 별도로 기록 |

파일 용량이 작아도 디코딩된 이미지 메모리는 클 수 있다. 예를 들어 RGBA 1024×1024 이미지 80장은 픽셀만 약 320MiB이고, 512×512 80장은 약 80MiB다. 배경·썸네일·PNG 작업 버퍼와 브라우저 부가 메모리는 별도다. 따라서 파일 압축뿐 아니라 실제 해상도와 동시 디코딩을 관리한다.

최적화 우선순위는 불필요한 투명 여백 제거 → 자산별 해상도 조절 → 썸네일 분리·지연 로딩 → 불필요한 화면 재계산 감소 → 움직임 제한 → 내보내기 메모리 관리다. 복잡한 이미지 여러 장을 미리 일괄 디코딩하지 않는다. 저장 실패나 PNG 실패는 성공으로 안내하지 않는다.

같은 조건을 최소 3회 반복하고 중앙값과 최악값을 기록한다. 75개가 기준을 충족하지 못하면 출시를 보류하고 최적화한다. 80개가 실패하고 75개가 통과하면 승인된 75개 이상의 구성으로 조정할 수 있으나, 수량 변경 후 완성 장면과 목록을 다시 확인한다. 제공한 스티커를 저사양 기기에서 숨기는 정책은 쓰지 않는다.

## 8. 제작 및 검증 단계

1. 이 80개 구성안, 빈 배경 시작, 분리 단위와 특별 효과 후보를 검토한다.
2. 대표 가구·화분 조립·책·작은 도구의 시안을 만들어 디자인 확인을 받는다.
3. 대표 자산 약 12개로 비례·터치·합성·메모리를 조기에 점검한다. 이 시험은 75개 실제 자산 시험을 대신하지 않는다.
4. 승인된 목록의 실제 자산을 제작하고 고유 ID·한국어·영어 이름·권리를 기록한다.
5. Sol로 앱 연결과 최적화를 진행한다. 세트 전환, 빠른 연속 입력, 저장 실패, 복원, 전체 사용과 PNG를 검사한다.
6. 실제 75개·80개 장면을 실기기에서 측정하고 최종 수량·지원 기기·효과 범위를 확정한다.
7. 사용자가 완성 장면을 확인한 뒤 다른 세트 제작에 같은 기준을 적용한다.

## 9. 서비스 전체와의 연결

공개 페이지는 한국어·영어 독립 URL과 기존 SEO 구조를 유지한다. 테마 설명·이용방법 이미지·특징 문구는 실제 출시 수량과 동작이 확정된 후 갱신한다. 준비 중인 수량을 현재 제공 중으로 표기하지 않는다.

1차는 계정 없이 기기 저장과 광고 수익 모델을 유지한다. 작업실에는 광고를 넣지 않는 기존 방향을 따른다. 성능 측정은 우선 개발용으로 수행하며 작품 내용이나 세부 배치 정보를 분석 서버에 보내지 않는다. 광고·Analytics·운영 정보·검색 등록·음원 권리 등 기존 배포 체크리스트는 별도 출시 조건으로 유지한다.

2차 결제와 이후 앱 개발을 위해 세트 ID와 버전, 구매 권한, 로컬 작품 데이터를 구분한다. 결제 단계 전에는 불필요한 개인정보를 미리 수집하지 않는다. 웹 성능 통과가 앱 성능 통과를 의미하지 않으며 앱 환경에서 저장·음악·PNG를 다시 검증한다.
